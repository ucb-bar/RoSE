Where the co-sim throughput actually goes

A controlled ablation over every architectural lever we tuned in the RoSE ↔ IsaacLab SoC co-sim — sync granularity, the synchronizer socket poll, lazy camera render, the MMIO vs DMA datapath, free-running vs barrier sync, and camera-free vs live-Isaac. One baseline, single-lever flips, all-new.

Headline. The two biggest throughput wins are host-side (the synchronizer socket poll, 7.1× on the per-grant barrier, measured now) and environment-side (lazy camera render, 3.9× on Isaac env.step). The FPGA datapath (MMIO→DMA) moves the per-grant sync barrier by ~0 ms — the barrier is a num_bytes=0 control-plane handshake, so DMA's value is on the orthogonal camera-payload axis, not throughput.

Now validated on silicon. The combined host+env fix was measured on the FPGA (garden capstone flight, 2 agreeing runs): 50.0 MHz full-run mean on the live co-sim — a 3.09× speedup over the 16.2 MHz baseline that beat the 37.1 MHz model (the real barrier + render taxes were smaller). At ~86% of the 60 MHz host-clock ceiling, the co-sim is now FPGA-emulation-bound — the goal.

What was run now, what is prior, what is computed

Runnable now — and run

The socket-fix axis needs no FPGA or GPU. The harness drove the real tracked gym_synchronizer + socket_thread against the rose_spike_sim bridge and timestamped every grant→RSP_STALL round-trip.

  • old 0.1: 115.5 ms/grant (send 105.1, rtt 10.3)
  • new 0.001: 16.3 ms/grant (send 6.1, rtt 10.2)

Reproduce: run_ablation.sh --now.

Measured prior — reused, not re-run

  • Free ceiling 59.9 MHz (FMR 1.0), barrier @5M 24.6 / @10M 34.3 MHz — FPGA recon sweep.
  • Render env.step 31.0→8.1 ms, physics floor 6.06 ms — direct GPU timing.
  • DMA metasim byte-exact (dma=PASS reqrsp=PASS).

The GPU is shared with a live capstone flight, so the render row reuses these rather than launching a competing Isaac session.

Computed — and scripted for FPGA

Effective-MHz rows follow one transparent model: wall = 13.8 s + (tcyc/step)×per_grant + ticks×env_step, validated against the measured anchors:

  • @5M model 24.2 vs measured 24.6 MHz
  • @10M model 34.5 vs measured 34.3 MHz
  • baseline warehouse model 16.0 vs anchor 16.2 MHz

The granularity sweep, socket-fixed FPGA points, and MMIO-vs-DMA rows are scripted for run_ablation.sh --fpga — not run (FPGA busy).

Why DMA is ~0 on the barrier

The grant→RSP_STALL handshake carries num_bytes=0. DMA replaces the per-word MMIO drain of served payload (sensor/camera words) with a 512-bit stream — it touches the payload-delivery path, not the control-plane barrier. Its win is camera-frame bandwidth within a granted step, a different axis than the per-grant tax. So the datapath choice does not move co-sim throughput; the host and env levers do.

Caveat — throughput validated, flight-path separately blocked

This report is about simulation throughput, which is validated end-to-end (measured 3.09× on silicon). It is not a claim about the 4-gate flight result. The full gate course is currently blocked by a separate, orthogonal guest-side vision-DMA stall (under investigation) — a flight-path / data-delivery issue on the guest, not a sync or throughput one. gates_passed is gated by that bug; the sync-barrier, render, and datapath findings here are unaffected by it.
